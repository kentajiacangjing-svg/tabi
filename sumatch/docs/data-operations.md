# データ運用手順（バックアップ・復元・デモデータ）

すべて `STORAGE_DIR`（既定 `./storage`）を対象にします。本番環境で実行する時は、実行前に必ず担当者の承認を取ってください。

## サンプルデータと実データの区別

- デモ用の初期データで作られたアカウント・会社には `is_demo = 1` が付きます
- この列がなかった古いデータベースでは、起動時に **デモ用の固定アドレス（`@demo.sumatch.jp` と `@<会社>.demo`）だけ** に印を付けます。それ以外のデータ（契約状態・金額・履歴など）は変更しません
- `DEMO_MODE` がオフの時、`is_demo = 1` の会社は公開画面・会社検索・会社ページに出ず、`is_demo = 1` のアカウントはログインできません（既存のログインも無効になります）

## 点検（読み取り専用）

```bash
STORAGE_DIR=./storage npm run db:inspect
```

デモ／実データのアカウント数、実データのお客様の相談・契約の件数、契約の状態別件数を表示します。`hasRealData: true` の時は、初期化・復元の前に必ずバックアップしてください。

## バックアップ

```bash
STORAGE_DIR=./storage npm run db:backup -- ラベル
```

- `backups/<日時>-<ラベル>/` に `sumatch.db`（`VACUUM INTO` による一貫したコピー）・`uploads/`・`manifest.json`（ハッシュ値と件数）を保存します
- アプリを止めずに実行できます。元のデータは変更しません
- 保存先は `BACKUP_DIR` で変えられます。バックアップには個人情報が含まれるため、アクセスできる人を限定してください

## 復元

```bash
# 1. アプリを停止する
# 2. 内容の確認（何も変更しない）
STORAGE_DIR=./storage npm run db:restore -- backups/<フォルダ>
# 3. 実行（現在のデータは自動で backups/<日時>-before-restore に退避）
STORAGE_DIR=./storage npm run db:restore -- backups/<フォルダ> --yes
# 4. アプリを起動する
```

マニフェストのハッシュ値と一致しないバックアップ（破損・改変）は復元しません。

## デモデータの初期化

```bash
STORAGE_DIR=./storage npm run db:reset            # 内容の表示だけ
STORAGE_DIR=./storage npm run db:reset -- --yes   # 実行（先に自動バックアップ）
```

- 実データ（デモ以外のアカウント・相談）があると **中止します**。本番環境の初期化には使えません
- 既定の動作（起動時など）でデータを自動削除することはありません
- 初期化後の次回起動で、`DEMO_MODE` に応じた初期データが作られます（オン：サンプル一式、オフ：カテゴリ・地域・料金プランのみ）

## 運営アカウント

デモモードでない環境では、サンプルの運営アカウントはありません。最初の運営アカウントは環境変数で作ります（運営が1人もいない時だけ、1回だけ作成）。

```bash
ADMIN_EMAIL=ops@example.com ADMIN_PASSWORD='12文字以上のパスワード' npm start
```

- パスワードは環境変数（ホスティングのシークレット設定）で渡し、コード・リポジトリ・ログに書かないでください
- アカウント作成後は `ADMIN_PASSWORD` を環境から外して構いません

## 既存案件のレビュー（要確認）

- `npm run db:inspect` の `contracts.needsReview` が、契約記録（契約書の双方確認）のない「工事中」「完了」の件数です（個人情報は出しません）
- 管理画面「成功報酬・要確認」に一覧が出ます。**自動では変更しません**
- 個別レビューの進め方（提案）：
  1. 対象案件ごとに、施工会社から契約書の写しを受け取る
  2. お客様にも内容を確認してもらう
  3. 運営が確認結果を記録する（記録のための画面は未実装。実装する場合は、既存の履歴に「運営による補完」として追記し、元の記録は変えない）
  4. 成功報酬の対象にするかは別途判断
- 作業の前に必ず `npm run db:backup` を実行してください

## 暗号化された項目とバックアップ

- 連絡先と訪問先住所は暗号化されています。バックアップを復元しても、**同じ `DATA_ENCRYPTION_KEY` がないと読めません**
- 鍵はバックアップとは別に保管してください。開発用の鍵ファイル（`STORAGE_DIR/.dev-encryption-key`）はバックアップに含まれません

## 既存の契約データへの影響（今回の変更）

- 今回の変更前に「工事中」「完了」になっていた契約は「双方の合意確認済み」として表示されます。契約書の登録・確認の記録がないため **「契約成立」にはならず、専用の連絡先欄も開きません**
- 「工事中」の案件は、そのまま「工事が終わった」にできます
- 金額・状態・履歴は自動では変更しません。これらの案件を「契約成立」として扱うかどうかは、承認のうえ個別に判断してください

## データ項目ごとの表示・保存（2026-10-21 時点）

「表示終了」と「削除・保存期間」は別のものです。保存期間は法務確認中で、確定していません。

| データ | 表示終了 | 削除・匿名化（実装） | 保存期間（要決定） |
|---|---|---|---|
| 現地調査の住所・メモ | 訪問日+7日、取り消し時 | 表示終了と同時に消去（1時間ごとの自動処理＋画面表示時） | — |
| 現地調査の予定・同意の記録（住所なし） | — | 残す | 要決定 |
| 契約後の連絡先 | 工事完了+90日、本人の削除時 | 表示終了と同時に削除（同上） | — |
| 連絡先の閲覧記録・運営の閲覧記録 | 運営のみ | 残す | 要決定（監査のため） |
| チャット・写真・見積・契約書 | 当事者と運営 | 削除処理なし | 要決定（紛争対応・取引記録） |
| アカウント（氏名・メール） | — | 退会は申請の受付のみ。削除・匿名化の処理は未実装 | 要決定 |
| 送信を止めた連絡先の記録（本文なし） | 運営のみ | 残す | 要決定 |
| 成功報酬の試算と変更履歴 | 運営のみ | 残す | 会計の保存期間（要確認） |
| ログインセッション | — | 期限切れを1時間ごとに削除 | — |
| 回数制限の記録 | — | 期間切れを1時間ごとに削除 | — |

- 自動消去は、各サーバープロセスで起動の30秒後と1時間ごとに動き、`POST /api/cron/purge`（`CRON_SECRET` 必須）でも実行できます。何度実行しても同じ結果です（冪等）
- 同意の撤回（現地調査の取り消し・連絡先の削除）の後も、チャット・通知・メールに住所や連絡先は入っていません（入らない設計で、テストで確認済み）。ブラウザのキャッシュも非公開ファイルは保存しない設定です

## 退会申請の処理手順（案・承認のうえで実施）

1. 管理画面「退会申請」で、進行中の相談・契約の有無を確認する
2. 進行中のものがあれば、利用者にアプリ内で確認する（工事中の契約は完了・解約の扱いを当事者と確認）
3. `npm run db:backup -- before-deletion` を実行する
4. 保存期間が決まっている記録（契約・取引など）は残し、それ以外の個人情報の削除・匿名化を行う（**処理の実装は保存期間の決定後**。それまでは手作業もしない）
5. 管理画面で「対応済み」にし、対応内容を記録する

## 鍵の交換（DATA_ENCRYPTION_KEY）

1. `npm run db:backup -- before-key-rotation`
2. 新しい鍵を作る（`openssl rand -base64 32`）。古い鍵を `DATA_ENCRYPTION_KEYS_OLD` に移し、新しい鍵を `DATA_ENCRYPTION_KEY` に設定して再起動
3. 古いデータは古い鍵で読め、新しく保存するものは新しい鍵で暗号化されます。旧データは書き換えません（失敗しても旧データは壊れません）
4. 全データを新しい鍵で書き直す処理は未実装です（必要になったら、バックアップを取ってから実装・実行）
5. 古い鍵は、古い鍵で暗号化されたデータが残っている間は削除しないでください

## 退会後の保持・削除・匿名化：仕様案と実装タスク（未実装・自動削除はしない）

保存期間が法務で決まるまで、**自動削除も手作業の削除も始めません**。以下は案です。

| データ | 退会時の扱い（案） | 理由 |
|---|---|---|
| アカウント（氏名・メール・パスワード） | ログイン不可にし、氏名を「退会済みユーザー」、メールを復元できない値に置き換える（匿名化） | 契約・取引の記録の相手方を残しつつ、本人を特定できなくする |
| 進行中の相談・会話 | 退会前に完了・取り下げを本人と確認。相手方には「退会済み」と表示 | 相手方の業務を止めない |
| 契約・契約履歴・成功報酬の記録 | 保存期間（法定・紛争対応・会計）まで保持。期間後に匿名化 | 法令・紛争対応・会計 |
| チャット本文・写真 | 保存期間まで保持し、期間後に削除 | 紛争対応 |
| 連絡先・訪問先住所 | 退会時にすぐ削除（すでに表示期限で消去される仕組みあり） | 必要がなくなる |
| 監査の記録（閲覧記録・db_audit） | 保持（個人情報は含まない） | 監査 |

実装タスク（保存期間の決定後）：
1. 退会処理（匿名化）の関数と、運営画面の「退会処理を実行」ボタン（確認画面・バックアップ確認つき）
2. 保存期間を過ぎた記録の匿名化・削除を、期限切れデータの自動消去（`lib/retention.ts`）に追加
3. 相手方の画面での「退会済みユーザー」表示
4. 単体テスト（匿名化後に本人を特定できる値が残らない、契約記録は残る）と E2E

## DB を直接操作した時の記録（db_audit）
- 契約（段階・状態・金額・見積・契約書・条件）、契約履歴（変更・削除＝改ざんの兆候）、成功報酬（状態・金額）、利用者（権限・状態・メール変更の有無）、会社（状態・プラン）の変更を、DBのトリガーが `db_audit` に記録します。アプリからの変更も、SQLite のツールで直接変更した場合も記録されます
- 個人情報（氏名・メール・住所・連絡先）は記録しません
- `db_audit` は SQL で変更・削除できません。ただし、DBファイルを丸ごと差し替える、トリガーを削除する操作は防げないため、ホスティングの Shell の利用者を限定し、利用記録を残してください
- 確認方法：`sqlite3 $STORAGE_DIR/sumatch.db "SELECT * FROM db_audit ORDER BY id DESC LIMIT 50"`（運営画面への表示は今後の課題）
