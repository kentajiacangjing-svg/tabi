# 公開構成の比較と推奨（限定テスト用）

> 料金・暗号化・スナップショットの数値は、2026-10-21 時点で **公式サイトを直接確認できていません**（この作業環境から各社サイトに接続できなかったため）。下表の数値は第三者のまとめ記事と記憶にもとづく目安です。申し込み前に必ず公式の料金ページ・ドキュメントで確認してください。

## SUMATCH の実装（リポジトリで確認した事実）

| 項目 | 内容 |
|---|---|
| フレームワーク | Next.js 15（App Router、`next build` → `next start` のサーバー型） |
| Node.js | 22.5 以上が必要（組み込みの SQLite `node:sqlite` を使うため）。`.node-version` = 22 |
| DB | SQLite（1ファイル、`STORAGE_DIR/sumatch.db`）。ORMなし |
| ファイル保存 | 写真・契約書は `STORAGE_DIR/uploads/` に保存（**永続ディスクが必須**） |
| 認証 | 自前のセッション（Cookie＋DB）。パスワードは scrypt |
| 定期処理 | サーバー内で1時間ごと（期限切れデータの消去）＋外部から呼ぶ `/api/cron/*`（`CRON_SECRET`） |
| リアルタイム | サーバー内のメモリで配信（SSE）→ **1台で動かす前提** |
| メール | 送信キューのみ（送信しない） |
| 前段のプロキシ | ホスティング側のもの。回数制限は `X-Forwarded-For` の右から `TRUST_PROXY_HOPS` 番目を接続元とする |

このため、**サーバーレス（Vercel・Netlify など）には向きません**。ファイルとDBが一時的なファイルシステムに置かれて消えるためです。「永続ディスク付きで1台のNode.jsサーバー」を動かせる構成が必要です。

## 候補の比較

| | A. Render（Web Service＋Persistent Disk） | B. Fly.io（Machine＋Volume） | C. 国内VPS（さくら・ConoHa など）＋自前の HTTPS |
|---|---|---|---|
| 操作 | ブラウザの管理画面だけで設定できる。`render.yaml` を用意済み | コマンドライン（flyctl）が中心 | サーバーの管理（OSの更新、HTTPS証明書、ファイアウォール）を自分で行う |
| HTTPS | 自動 | 自動 | 自分で設定（Caddy などで自動化は可能） |
| 永続ディスク | あり（有料プランのみ。1台・ゼロダウンタイムデプロイ不可と記憶。要確認） | あり（Volume、1台のマシンに1つ） | あり（サーバーのディスク） |
| 保存時暗号化 | **要確認**（公式ドキュメントで確認） | **要確認**（Volume は暗号化されると記憶。要確認） | 事業者による。自分でディスク暗号化を設定する場合あり |
| 自動バックアップ | ディスクの自動スナップショットあり（頻度・保存期間は要確認） | Volume の自動スナップショットあり（2026年から有料との記事あり。要確認） | 事業者のオプション、または自前 |
| 東京リージョン | なし（近いのはシンガポール。要確認） | あり（東京） | あり（国内） |
| 概算費用（目安・要確認） | Web Service Starter 月7ドル前後＋ディスク 1GBあたり月0.25ドル前後 | 小さいマシン 月2ドル前後＋メモリ追加＋Volume 1GBあたり月0.15ドル前後＋スナップショット | 月500〜1,500円程度から（事業者・プランによる） |
| ロックイン | 低い（普通の Node.js アプリ。`render.yaml` だけが固有） | 低い（`fly.toml` が固有） | ほぼなし |
| 運用リスク | 低い。1台なので再デプロイ時に短い停止あり | 中。コマンド操作に慣れが必要 | 高い。セキュリティ更新・監視・証明書を自分で管理 |

## 推奨：A. Render（限定テストの段階）

- オーナーがブラウザ操作だけで準備でき、HTTPS・ディスク・スナップショット・ヘルスチェックがまとめて使えるため、少人数の限定テストに最も向いています
- 注意点（申し込み前に確認）：
  1. **個人情報の保存場所が海外（シンガポール）になる** → プライバシーポリシーで「外国にある第三者への提供／保管」の説明が必要か、法務に確認（[legal-review-checklist.md](./legal-review-checklist.md)）。国内保存が必要なら B（東京）か C
  2. 保存時暗号化とスナップショットの保存期間を公式ドキュメントで確認し、結果をこの文書に追記
  3. スナップショットは同じ事業者内の保管。**別の場所へのバックアップ（オフサイト）** は未整備（後述）
- 一般公開の段階では、利用者数・国内保存の要否・費用を見て再検討します

## Render での準備手順（オーナーが行う。費用が発生する操作には 🔒）

1. Render のアカウントを作成し、GitHub と連携する（🔒 有料プランの選択は承認のうえで）
2. 管理画面で「New」→「Blueprint」を選び、このリポジトリ（`kentajiacangjing-svg/tabi`）とブランチを選ぶ → `render.yaml` の内容（`sumatch-beta`、1GBディスク）が表示される
3. 表示された環境変数のうち「sync: false」のものを入力する（下の一覧）。**値はチャットやメールに書かない**
4. 作成後、「Logs」で起動を確認し、表示されたURLの `/api/health` が `{"ok":true}` を返すことを確認
5. 運営アカウントでログインできたら、`ADMIN_PASSWORD` を削除して再デプロイ
6. 「Cron Job」を追加：毎日 `curl -X POST -H "Authorization: Bearer $CRON_SECRET" <URL>/api/cron/purge`（`/api/cron/reminders` も同様）
7. 外部の監視サービス（無料のもので可）に `<URL>/api/health` を登録

## 環境変数の一覧

| 名前 | 必須 | 内容 | 作り方・注意 |
|---|---|---|---|
| `STORAGE_DIR` | ○ | DB とファイルの保存先（永続ディスク上） | `render.yaml` で `/var/data/storage` |
| `BACKUP_DIR` | ○ | `npm run db:backup` の保存先 | `/var/data/backups`（同じディスク。オフサイトは別途） |
| `DATA_ENCRYPTION_KEY` | ○ | 連絡先・住所の暗号化キー | `openssl rand -base64 32` で作り、パスワード管理ツールにも保管。**なくすと復元できない** |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | 初回のみ | 最初の運営アカウント | パスワードは12文字以上。作成後は `ADMIN_PASSWORD` を削除 |
| `APP_URL` | ○ | 公開URL（https） | Cookie に Secure が付く |
| `CRON_SECRET` | ○ | `/api/cron/*` を呼ぶための合言葉 | 長いランダム文字列 |
| `SITE_BASIC_AUTH` | 限定テスト中は○ | サイト全体のパスワード（`ユーザー名:パスワード`） | 参加者にだけ伝える。設定中は検索エンジンにも載らない（noindex） |
| `TRUST_PROXY_HOPS` | ○ | 前段のプロキシの数 | Render は `1`（要確認）。直接公開するなら `0` |
| `DEMO_MODE` | 設定しない | サンプルデータとデモログイン | 本番では既定でオフ |
| `MAIL_TRANSPORT` | 設定しない | メール送信 | 未設定＝送らない |
| `AI_DRAFT_ENABLED` / `ANTHROPIC_API_KEY` | 設定しない | AI下書き | 既定でオフ |
| `ROBOTS_NOINDEX` | 任意 | `true` で検索エンジンに載せない | `SITE_BASIC_AUTH` 設定中は自動 |

## バックアップと復元

- 1次：ホスティングのディスクスナップショット（自動）
- 2次：`npm run db:backup`（Render の「Shell」から実行）。同じディスクに保存されるため、ディスク障害には弱い
- **未整備（P1）**：別の場所への定期バックアップ。案：外部ストレージ（S3互換）に暗号化して送る処理を追加する（ストレージのアカウント作成が必要なため承認待ち）。それまでは週1回、Render の Shell から `backups/` の最新フォルダを手元に保存する手順で代替（個人情報を含むため保管場所に注意）
- 復元訓練：限定テスト前に1回、別の Render サービス（またはローカル）に `npm run db:restore -- <フォルダ> --yes` で戻し、ログインと画面表示を確認

## 監視・ログ
- `/api/health` は DB に読みに行けるかだけを返し、バージョンや設定は返しません。サイトのパスワード（`SITE_BASIC_AUTH`）の対象外です
- サーバーのログには、エラーの種類とメッセージだけを出し、入力内容・本文・連絡先は出しません。Render の「Logs」で確認できます
